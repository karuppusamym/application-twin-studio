Application Twin Studio — playable demo

A browser-only simulation of the idea. The real studio (Python) runs the same scenarios against real HTTP, web and TN3270 twins.

Does the converted automation behave like the original?

The UiPath bot drives the web UI and the 3270 mainframe screen. Its agentic replacement uses the API and the same mainframe. Each gets its own copy of the twin, seeded identically. Independent expected results decide — not whether the two bots agree with each other.

How the real studio works

  1. Onboard — a UiPath project is parsed statically (nothing is executed). Every activity is mapped to a twin operation, or kept as an explicit gap. Unsupported steps (IE, desktop apps, custom code) block readiness instead of being skipped.
  2. Twin — each application is described in a reviewed YAML spec: entities, state transitions, operations built from allowlisted steps, web pages with stable selectors, and 3270 screens. One state model sits behind the API, the UI, the terminal and SQL.
  3. Environment — every run gets its own isolated copy: separate databases, token, fault schedule, clock and TN3270 port.
  4. Run — the original automation runs in environment A, the replacement in B, from the same fixture and fault schedule.
  5. Judge — hand-written expected outcomes are checked against final state, events and outputs; then A and B are diffed. A deliberately wrong twin rule or a defective replacement must fail.
  6. Certificate — the result states its confidence. Demonstration rules and simulated replay can only ever be exploratory.
What this demo does not show: the real HTTP gateway, real TN3270 protocol bytes, XAML import, and the gap register. Start the studio with python -m ats serve for those.
